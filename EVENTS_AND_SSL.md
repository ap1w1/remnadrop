# События, уведомления и SSL

Раздел **Обзор → События** хранит изменения состояния нод, запуск и ошибки
автоматизаций, напоминания об оплате, события SSL и предупреждения мониторинга
(ЦП, ОЗУ, падение онлайна и трафика, включая восстановление).
Пороговые значения и число подтверждающих замеров остаются в настройках мониторинга.
События начинают накапливаться после установки миграции; старая история не импортируется.

Кнопка **События** перед Telegram показывает число непрочитанных уведомлений.
При открытии журнала счётчик сбрасывается для текущего администратора; сами события
сохраняются. Новые события после просмотренного снимка остаются непрочитанными.
Фильтры по типу и важности не изменяют общий счётчик. Журнал обновляется каждые 15 секунд.

## Браузер и Web Push

В **Настройки → Уведомления** можно включить уведомления при открытой панели,
выбрать типы событий и подключить фоновые push на текущем устройстве.
Разрешение браузера запрашивается только после нажатия пользователем.
Отклонённое разрешение нужно изменить в настройках сайта в браузере.
Выбор типов хранится на сервере отдельно для каждого администратора и применяется
к обоим каналам. Регистрация Web Push принадлежит конкретному браузеру.

Для фоновых уведомлений требуется HTTPS и поддержка Web Push. На iPhone/iPad
панель нужно добавить на домашний экран и открывать оттуда. Доставку определяет
браузер и ОС: закрытая вкладка допустима, полностью выключенный браузер или режим
«Не беспокоить» могут задерживать показ. См. [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).

Один раз сгенерируйте VAPID-ключи в каталоге backend:

```sh
npx web-push generate-vapid-keys
```

Добавьте в окружение API и scheduler:

```dotenv
WEB_PUSH_PUBLIC_KEY=<public key>
WEB_PUSH_PRIVATE_KEY=<private key>
WEB_PUSH_SUBJECT=mailto:admin@example.com
```

Сохраняйте ключи между обновлениями и резервируйте их вместе с секретами панели.
Закрытый ключ API не возвращает. Подробности: [web-push](https://github.com/web-push-libs/web-push).
После изменения ключей повторно подключите устройство в настройках.
При явном выходе из панели подписка этого браузера отключается.
Неподдерживаемые браузеры и отсутствие серверной конфигурации отображаются в настройках.

Push доставляет scheduler из постоянной очереди: до 12 попыток с паузой до часа.
Ответы сервиса push 404/410 удаляют недействующую подписку. Для одного администратора
можно зарегистрировать до 20 устройств. Выключенные типы отбрасываются даже для уже
поставленных в очередь сообщений. Одновременные вкладки используют общий курсор и
Web Locks; при включённом push уведомления открытой панели не дублируют его.

## SSL-сертификаты

Раздел **Ноды → SSL-сертификаты** позволяет добавить название и домен сертификата,
выбрать одну или несколько нод, дату окончания и сроки напоминаний, например `3, 2, 1`.
Это ручной учёт: чтение файлов на нодах, выпуск/продление сертификатов и загрузка
закрытых ключей не выполняются.

Расчёт ведётся по календарным дням UTC. В начале указанной даты сертификат считается
истёкшим. Scheduler проверяет сроки каждые 30 секунд и записывает:

- `ssl.expiring` — достигнут выбранный срок предупреждения;
- `ssl.expired` — наступила дата окончания, отдельное обязательное уведомление.

Каждый срок создаёт событие один раз для сочетания ID сертификата и даты окончания.
После простоя приходит ближайшее актуальное напоминание, без пачки уже пропущенных
сроков. После продления достаточно обновить дату. Выключенные сертификаты и записи,
у которых удалены все ноды, не создают напоминаний. Удаление записи сохраняет журнал.

Вебхуки используют отдельное окружение или существующий общий канал:

```dotenv
SSL_WEBHOOK_URL=https://hooks.example.com/ssl
SSL_WEBHOOK_SECRET=<at least 32 characters>
```

Допускается несколько HTTPS-адресов через запятую. Если `SSL_WEBHOOK_URL` пуст,
используется `WEBHOOK_URL` при `WEBHOOK_ENABLED=true`. Если `SSL_WEBHOOK_SECRET`
пуст, используется `WEBHOOK_SECRET_HEADER`. Адреса должны разрешаться в публичные
IPv4 и использовать порт 443. Необходимая конфигурация должна быть задана до
наступления напоминания; старые события не отправляются задним числом.

Пример полезной нагрузки:

```json
{
  "id": "42",
  "event": "ssl.expiring",
  "occurredAt": "2026-11-23T00:00:00.000Z",
  "data": {
    "certificateId": "00000000-0000-4000-8000-000000000001",
    "name": "Edge TLS",
    "domain": "vpn.example.com",
    "nodeUuids": ["00000000-0000-4000-8000-000000000002"],
    "expiresOn": "2026-11-26",
    "reminderDays": 3,
    "daysRemaining": 3
  }
}
```

Подпись соответствует другим вебхукам форка: `X-Webhook-Signature` содержит
`sha256=<HMAC-SHA256(secret, timestamp + "." + rawBody)>`, время — в
`X-Webhook-Timestamp`, идентификатор — в `X-Webhook-Event-Id`.
Получатель должен проверять подпись и обрабатывать повторную доставку по ID.
Очередь хранится в PostgreSQL, повторяет до 20 попыток, а каждый адрес подтверждается
отдельно. Успешная доставка требует HTTP 2xx; перезапуск панели очередь не теряет.

## Обновление и проверки

Миграция `20261123120000_panel_events_ssl` добавляет журнал, прочтения, предпочтения,
подписки, очереди, сертификаты и транзакционные триггеры на изменение состояния нод,
предупреждения метрик и выполнение автоматизаций. Перед запуском новой версии
примените стандартный `prisma migrate deploy` через существующую процедуру обновления.
Само изменение исходников рабочую панель не обновляет.

После сборки backend:

```sh
node --test scripts/panel-events.test.cjs
```

Тесты работают в изолированной PGlite/PostgreSQL и не отправляют внешних уведомлений.
CI также проверяет production-интерфейс с тестовым API: сброс счётчика, фильтры,
создание/продление SSL, запрос разрешения браузера, сохранение типов и плитки
редактора пользователей на широком и мобильном экранах.
