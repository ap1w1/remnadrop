# RemnaDrop — резервные копии

Этот модуль добавляет интерфейс **«Бэкапы»** и независимый агент systemd.

## Что сохраняется

Снимок PostgreSQL через `pg_dump -Fc`. **Это не полный образ сервера.** В дамп не входят секреты Docker Compose, `.env`, TLS-ключи, объекты внешнего хранилища и конфигурация rclone. Их нужно сохранять отдельно (в защищённом месте).

## Хранилища

- Local: `/var/lib/remnadrop-backups/archives/<папка>/<UUID цели>/*.dump`.
- S3: настроенный rclone remote (через AWS S3/S3-compatible API).
- FTP / SFTP / FTPS: настроенный rclone remote; **обычный FTP без TLS небезопасен** для копий БД.
- Google Drive: заранее созданный rclone remote через OAuth; токены и пароли в браузер не отправляются.

Для удалённых хранилищ на сервере нужно установить `rclone` и создать конфигурацию только для root:

```bash
sudo apt-get install -y rclone
sudo install -d -m 700 /etc/remnadrop-backups
sudo rclone --config /etc/remnadrop-backups/rclone.conf config
sudo chmod 600 /etc/remnadrop-backups/rclone.conf
sudo rclone --config /etc/remnadrop-backups/rclone.conf listremotes
```

При создании хранилища в панели укажите **имя** созданного remote (`mys3`, `ftp-backup`, `gdrive1`). Серверные токены не копируйте в веб-интерфейс.

## Индивидуальные настройки

Каждое хранилище имеет своё расписание в минутах (15—525600), срок хранения (1—3650 дней), лимит объёма, автоудаление старых копий и переключатель вебхука. Один интервал не влияет на другие хранилища. Кнопка «Создать сейчас» назначает ближайший запуск.

Лимит объёма проверяется перед загрузкой по локальной папке или `rclone size`. Если не удаётся точно измерить размер удалённого хранилища, копирование прекращается; превышать лимит без подтверждения нельзя. При автоматической очистке удаляются **только архивы данного назначения, зарегистрированные агентом**, причём последняя успешно созданная копия защищена. Не храните в управляемой подпапке файлы сторонних приложений.

## Агент

Установщик `upgrade-fork.sh` после успешного переключения панели создаёт `remnadrop-backups.timer` на сервере, который проверяет расписания каждую минуту. Отдельный процесс выполняет `pg_dump`, копирование/проверку, очистку и регистрацию результата. Панели **не предоставляется Docker socket**.

Проверка:

```bash
sudo systemctl status remnadrop-backups.timer
sudo systemctl start remnadrop-backups.service
sudo journalctl -u remnadrop-backups.service -n 100 --no-pager
```

Если панель уже обновлена, агент можно установить вручную из каталога извлечённого форка:

```bash
sudo bash backup-agent/install-agent.sh
```

## Вебхук

У каждого хранилища переключатель «Отправлять вебхук». Адрес и HMAC-секрет задаются системным администратором в `/etc/remnadrop-backups/agent.env` и применяются после следующего запуска задачи:

```text
BACKUP_WEBHOOK_URL=https://example.org/hooks/backups
BACKUP_WEBHOOK_SECRET=long-random-secret
```

События: `backup.completed` и `backup.failed`; JSON содержит `targetId`, `runId`, `storageType`, `name`, `fileName`, `sizeBytes`, `sha256`, `error`, `occurredAt`. При наличии секрета тело подписано заголовком `X-Remnadrop-Signature: sha256=<HMAC-SHA256>`. Сбой доставки не отменяет успешно созданную копию; ошибок доставки следует искать в журнале агента.

## Восстановление

Восстановление **не автоматизировано** в этой версии. Оно должно выполняться в отдельной тестовой PostgreSQL-базе с проверкой целостности дампа, а затем по регламенту с согласованной остановкой панели. Никогда не применяйте `pg_restore --clean` к рабочей БД без полной проверенной копии и плана отката.

## Дополнительные рекомендации

Используйте независимые хранилища и, при необходимости, rclone crypt для шифрования удалённых копий. Мониторинг статуса и заполнения отражает последний успешный замер (не непрерывный live мониторинг), а резервная копия может содержать персональные данные пользователей и API-секреты.
