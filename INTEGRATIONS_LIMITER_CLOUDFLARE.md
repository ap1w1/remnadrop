# RemnaDrop: Limiter, Cloudflare и автоматизации

## Limiter

**Инструменты → Limiter** открывается на последних событиях. Настройки находятся
по кнопке **Настройки** на отдельной странице, как в мониторинге.

В нарушении доступны пользователь, подписка, лимит, обнаруженное число устройств,
уникальные IP, соединения, повторения за 24 часа и время. Раскрытая карточка
показывает IP, провайдера, ноды и дополнительные сведения из события. История
включает нарушения лимитов, трафиковые события, общий HWID и ежедневные отчёты.
Старые события сохраняются; отсутствующие в них сведения не выдумываются.

Действия используют тот же обработчик и состояние, что кнопки Telegram:

- сбросить подключения;
- отключить пользователя постоянно или на выбранный срок;
- восстановить пользователя;
- игнорировать постоянно или на выбранный срок;
- отменить игнорирование.

Срок игнорирования, очередь восстановления и ручные действия видны обоим
интерфейсам. Повтор запроса с тем же requestId возвращает сохранённый результат.
Отдельный журнал показывает источник и результат действия. Исключения и сводная
статистика доступны из раздела Limiter.

В **Настройки → Уведомления** переключатель **Дублировать события и действия в
Telegram** управляет отправкой уведомлений в бот. При включении Telegram также
получает уведомления о действиях из панели. При выключении токен остаётся
сохранённым, события и действия продолжают записываться в панели. Команды бота
и существующие кнопки остаются доступны. Дублирование уведомления не запускает
блокировку повторно; повторная отправка запроса не создаёт второе уведомление.

### Webhook Limiter: текущее поведение

**Входящий webhook уже реализован.** Встроенный Go Limiter отправляет в RemnaDrop
подписанные события через внутренний `POST /api/limiter-webhook`. Это не
публичный исходящий webhook в произвольную внешнюю систему.

Поддерживаемые типы событий:
`violation_detected`, `soft_violation_detected`, `traffic_spike`,
`traffic_heavy`, `shared_hwid`, `daily_report`, `update_available`,
`action`, `settings_changed`.

Подпись проверяется по исходному JSON-телу: HMAC-SHA256 от
`timestamp + "." + rawBody` с внутренним секретом Limiter. Заголовки:
`X-Timestamp` (Unix seconds) и `X-Signature-V2` (hex HMAC, допускается
префикс `sha256=`). Окно времени ±300 секунд, лимит тела — 2 МиБ.
Дублирующиеся события нарушений отбрасываются по SHA-256 отпечатку
подписанного содержимого, действия — по `requestId`.

**Исходящий webhook Limiter реализован отдельно от внутреннего Go→panel webhook.**
Он отправляет подписанные события в один заранее заданный публичный HTTPS endpoint.

Добавьте **в окружение процесса RemnaDrop**, не в контейнеры нод:

```dotenv
LIMITER_OUTBOUND_WEBHOOK_URL=https://example.com/api/limiter/events
LIMITER_OUTBOUND_WEBHOOK_SECRET=replace-with-your-own-random-secret-of-at-least-32-chars
LIMITER_OUTBOUND_WEBHOOK_EVENTS=violation_detected,soft_violation_detected,action,traffic_spike,traffic_heavy,shared_hwid,daily_report,update_available,settings_changed
```

После изменения окружения пересоздайте соответствующий контейнер панели.
Не публикуйте HMAC-секрет в чате, репозитории или логах.

Метод `POST`, тело:

```json
{"id":"event-uuid","event":"violation_detected","occurredAt":"2026-11-23T00:00:00Z","data":{"user":{"uuid":"user-uuid","id":114644,"username":"example"},"violation":{"deviceLimit":5,"observedCount":9,"uniqueIpCount":9,"connectionCount":12,"violations24h":3,"ips":[]}}}
```

Пример **иллюстративный**, поля зависят от типа события; IP-адреса могут
передаваться получателю (максимум 100 IP за событие), поэтому настраивайте
только собственный защищённый endpoint с соответствующей политикой хранения.

Заголовки: `X-Webhook-Event-Id`, `X-Webhook-Timestamp` (Unix seconds),
`X-Webhook-Signature` (строка `sha256=<hex>`).
Подпись: `HMAC-SHA256(secret, timestamp + "." + rawBody)`.
Получатель должен проверять подпись с постоянным временем сравнения,
допустимое окно времени и дедуплицировать `X-Webhook-Event-Id`.

Выбор типов — опциональный `LIMITER_OUTBOUND_WEBHOOK_EVENTS`.
Если переменная не задана, отправляются все поддерживаемые типы.
События ставятся в PostgreSQL-очередь, повторная доставка при ошибках
с экспоненциальной задержкой, до 12 попыток. Последние успешные записи
удаляются через 7 дней. Endpoint проверяется на публичный IPv4, HTTPS
порт 443, TLS-сертификат и отсутствие URL-логина/пароля. Редиректы
не выполняются. Если поменять URL получателя, события прежнего URL не
переотправляются на новый.

В панели: **Limiter → Настройки → Уведомления** — статус получателя,
число ожидающих, доставленных и исчерпавших попытки. API администратора:
`GET /api/limiter/outbound-webhook/status` без вывода HMAC-секрета.

Внутренний `/api/limiter-webhook` **нельзя** использовать как публичную
точку приёма уведомлений сторонних систем.

### Настройка

1. Откройте **Limiter → Настройки**.
2. Укажите режим, лимиты и интервалы. По умолчанию Limiter выключен, режим ручной.
3. При необходимости настройте подсети/ASN, исключения IP/CIDR, пользователей и
   нод, трафиковые проверки, общий HWID и ежедневные отчёты.
4. Включите Limiter и сохраните настройки. Запуск/остановка применяются при
   следующей проверке состояния, обычно в течение 30 секунд.

**Telegram необязателен.** Для уведомлений и бота добавьте Bot Token, Chat ID и
Admin IDs в настройках. MaxMind License Key также необязателен. Секреты
шифруются AES-256-GCM и не возвращаются в ответы API. Ключ шифрования
REMNADROP_LIMITER_ENCRYPTION_KEY (32+ символа), а при его отсутствии APP_SECRET
или JWT_AUTH_SECRET, должен сохраняться при переносе БД.

Автоматический режим и временные блокировки требуют сохранения Valkey/Redis
через AOF или RDB. Очередь восстановления находится в DB 8. Проверка AOF/RDB
не заменяет постоянный volume. Выключение при незавершённых временных блокировках
отклоняется: сначала восстановите пользователей или дождитесь окончания сроков.

### Адаптер upstream

Используется исходный код [syvlech/remnawave-limiter](https://github.com/syvlech/remnawave-limiter)
5.1.0 на коммите c5ce367c5f38a345fad59bb813fd9fd67c80a329.
scripts/patch-limiter.py добавляет адаптер RemnaDrop. Несоответствие ожидаемым
точкам исходного кода останавливает сборку.

Адаптер повторно использует обработчики действий, настройки, мониторинг и очередь
восстановления upstream. Он добавляет работу без Telegram, полные события панели
и авторизованный локальный Unix-сокет управления. Открытого TCP-порта управления
нет. Внутренние Bearer/HMAC-ключи случайные и создаются при запуске API.
Go-процесс работает с UID/GID 10001. Используется подключение панели к Redis
(REDIS_SOCKET либо REDIS_HOST/REDIS_PORT) и отдельная логическая DB 8.

## Cloudflare DNS

Главный экран показывает **аккаунты → домены → DNS-записи**. Есть поиск по
домену/IP/ноде, фильтры аккаунта/типа, страницы длинных списков и журнал.
Ошибка одного аккаунта или зоны не скрывает данные остальных.

### Несколько аккаунтов

Откройте **Cloudflare DNS → Настройки → Добавить аккаунт**. Задайте имя и
API-токен с разрешениями **Zone Read, DNS Read, DNS Edit** для нужных зон.
Повторите для остальных аккаунтов. Поддерживаются пользовательские токены и
account-owned tokens. Доступ проверяется списком зон; загружаются все страницы
зон и записей.

Токены шифруются отдельно. Ключ — CLOUDFLARE_DNS_ENCRYPTION_KEY (32+ символа)
с альтернативой APP_SECRET / JWT_AUTH_SECRET. Старый единственный токен
переносится в отдельный аккаунт вместе с привязками и историей. Удаление
аккаунта сохраняет журнал DNS-операций. Включённые автоматизации с этим
аккаунтом нужно сначала остановить.

### Ручная смена IP

Раскройте домен, выберите A/AAAA-запись и нажмите **Изменить IP**. Привязка к
ноде для явно выбранной записи не требуется. Запрос содержит accountId, zoneId,
recordId, expectedOldIp и newIp. Перед PATCH проверяются аккаунт, зона, имя,
тип записи и ожидаемый старый IP. Меняется только адрес; TTL и проксирование
сохраняются. Повторная проверка не является атомарным CAS со сторонним
редактором Cloudflare.

### Автоматизация DNS

В меню записи выберите **Создать автоматизацию** или добавьте действие
**Изменить IP домена** в конструкторе. Выбираются аккаунт, домен, запись и
источник адреса: заданный IP либо результат предыдущего действия
**Сменить IP ноды**. Для заданного IP нода не обязательна.

Сохраняется синхронизация привязанных к ноде записей: включите домен в
**Настройки → Синхронизация с IP нод** и соответствующий переключатель
действия **Сменить IP ноды**. Она меняет только разрешённые A-записи с совпадающим
старым IP. Общие записи нескольких нод отклоняются. Сопоставляются адрес хоста,
CNAME и явные связи аккаунт/зона/запись/хост; SNI не используется.

Аккаунтами и привязками управляет администратор. Endpoint
POST /api/cloudflare-dns/records/replace-ip требует отдельного API-права
hosts:cloudflare-record-write. Старый POST /api/cloudflare-dns/replace-ip
и hosts:cloudflare-replace-ip сохраняют обязательную привязку к ноде.

Входящий webhook /api/cloudflare-dns/webhook/node-ip-changed использует
CLOUDFLARE_DNS_INCOMING_SECRET, HMAC исходного тела, время и защиту от повторов.
Исходящий CLOUDFLARE_DNS_IP_UPDATED настраивается переменными
CLOUDFLARE_DNS_WEBHOOK_URL и CLOUDFLARE_DNS_WEBHOOK_SECRET.

## Автоматизации

Конструктор: **Условие → Действия → Проверка**.

Условия: падение онлайна, недоступность ноды, интервал, ручной запуск.
Действия: DPI-проверка, смена IP ноды, смена IP DNS-записи, скрытие/показ хостов,
подписанный HTTPS-вебхук. До восьми действий выполняются в заданном порядке.
При ошибке можно остановить следующие действия либо продолжить.

Предварительная проверка только читает состояние: не изменяет DNS/хосты,
не создаёт платных DPI-заданий и не выполняет сценарий. Ручной запуск требует
подтверждения. Доступны редактирование, копирование, переключение состояния,
поиск и журнал по шагам. История сохраняется после удаления правила.

Изменение и запуск правил доступны администратору. Токены с правами только на
ноды не получают доступ к Cloudflare через автоматизацию. Одновременные
запуски защищены арендой выполнения и версией правила. Старые правила
сохраняют параметры, состояние и порядок действий. Отсутствующие или
устаревшие метрики не считаются подтверждением недоступности ноды.

### Новые условия и география проверки (PR #3)

Условие `online_value` принимает сравнение `gt`, `lt`, `eq` с целым
порогом от 0 до 1000000. Срабатывание проверяется только по свежим,
достоверным метрикам доступной ноды. В UI это «Онлайн больше/меньше/равно N».
Существующие правила `online_drop` продолжают сравнивать падение в процентах.

Действие `dpi_check` может принимать `pop_ids` — непустой список
уникальных положительных ID точек (до 100) одной выбранной страны.
Если список опущен, DPI Checker выбирает оптимальные точки. Редактор
показывает поиск по городам, регионам и операторам через API `/pops`.

**Не путать запуск DPI-задания с подтверждением недоступности!** Текущий
исполнитель после успешного `dpi.start()` продолжает следующие действия.
Ветвление по завершённым DPI-результатам и счётчику недоступных регионов
в этом PR ещё не реализовано. **Не создавайте цепочки DPI → rotate_ip →
Cloudflare DNS для автоматического реагирования**, пока не внедрён
сохраняемый условный исполнитель с проверкой фактического результата
(см. GitHub issue #4). Ручной просмотр результата остаётся безопасным путём.

### Повторная сборка

В Dockerfile включены BuildKit cache mounts для `/root/.npm`,
`/go/pkg/mod` и `/root/.cache/go-build`. Изменения миграций больше не
инвалидируют npm install backend. Кэш помогает только при сохранении
данных builder между запусками; `docker builder prune --all` удаляет
такой кэш. Сборка на сервере с 2 ГиБ ОЗУ остаётся ресурсоёмкой;
кэширование не заменяет достаточные ОЗУ и дисковое место.

## Обновление и проверки

    sudo remnadrop check
    sudo remnadrop update && sudo remnadrop status

Установщик создаёт резервные копии, проверяет восстановление PostgreSQL,
выполняет миграции и пересоздаёт панель. Проверяются фактический ID образа,
health и HTTP. Базовая версия остаётся 2.8.1; версию форка определяет Git-ревизия.

Workflow Integrations QA собирает Go/NestJS/frontend, выполняет регрессионные
тесты, мигрирует базовые 128 миграций через предыдущую версию с сохранёнными
данными, проверяет повторный deploy, настоящий API и Go-процесс без Telegram.
Browser smoke открывает production frontend на desktop/mobile с синтетическими
API-данными. Внешние Cloudflare/Telegram-токены и реальные ноды в CI не используются.
