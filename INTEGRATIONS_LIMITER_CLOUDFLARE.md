# RemnaDrop 2.8.1: встроенный Limiter 5.1.0 + Cloudflare DNS

Интеграция сохраняет внешний API панели 2.8.1. Перед эксплуатацией нужны успешные проверки CI, миграция на восстановленной копии PostgreSQL и проверка выбранных функций с тестовым пользователем и нодой.

## Архитектура: панель и Limiter в одном Docker-контейнере

Образ `panel-fork:...` содержит **оригинальный Go-бинарник [syvlech/remnawave-limiter 5.1.0](https://github.com/syvlech/remnawave-limiter/releases/tag/5.1.0)** по пути `/usr/local/bin/remnawave-limiter`, системные CA-сертификаты для HTTPS к Telegram/MaxMind и базу часовых поясов. **По умолчанию Limiter выключен, выбран ручной режим.**

- Когда в **Инструменты → Limiter** переключатель выключен, Go-процесс отсутствует.
- Когда включён — NestJS проверяет настройки, запускает Go Limiter дочерним процессом **в том же контейнере `remnawave`**, наблюдает за его завершением, обновляет статус и перезапускает при изменении настроек. Настройки применяются при следующей проверке, обычно в течение 30 секунд.
- Используется существующее подключение панели: `REDIS_SOCKET` для Unix-сокета либо `REDIS_HOST` + `REDIS_PORT` для TCP, включая IPv6. При наличии применяется `REDIS_PASSWORD`; для состояния Limiter всегда выбирается отдельная логическая **DB 8**. Дополнительный Docker-сервис Limiter не требуется.
- Для безопасности `LimiterBridgeSecretsService` генерирует временные случайные внутренние Bearer/HMAC ключи при каждом запуске API. Они передаются только дочернему процессу. `REMNADROP_LIMITER_BRIDGE_TOKEN` и `REMNADROP_LIMITER_WEBHOOK_SECRET` **задавать вручную не требуется**.
- Внутренние обращения идут через loopback. API совместимости проверяет внутренний Bearer-ключ, `/api/limiter-webhook` — HMAC исходного тела запроса. Для остальных обращений требования панели к reverse proxy и HTTPS сохраняются.
- При ошибке запуска (нет Telegram-секретов, Valkey недоступен, бинарник отсутствует) **панель продолжает работать**, а причина выводится в настройках Limiter.
- При остановке панели встроенный Limiter тоже останавливается.

Процесс Limiter работает с UID/GID `10001`; для Unix-сокета у него должны быть права подключения.

**Автоматический режим требует AOF или RDB.** В Redis хранятся очереди автовосстановления отключённых пользователей; runner отказывается запускать автоблокировку при отключённых механизмах сохранения. Данные Redis должны находиться на постоянном хранилище, а их сохранение после перезапуска необходимо проверить отдельно. Проверка AOF/RDB не доказывает наличие постоянного Docker volume. Ручной режим доступен без этого требования.

### Совместимость API 5.1.0 → Remnawave 2.8.1

У Limiter 5.1.0 другой API. `LimiterBridgeController` предоставляет следующие адаптированные endpoints:

| Upstream API | Вызов в RemnaDrop 2.8.1 |
|---|---|
| `GET nodes` | Таблица nodes |
| `POST/GET connections/by-node` | Очереди `fetch-users-ips` |
| `GET users/:id` | Users по `t_id` + InternalSquads |
| `POST users/:id/actions/disable,enable` | `UsersService` |
| `POST connections/drop` | Очереди нод |
| `GET hwid/devices` | Таблица `hwid_user_devices` |
| `GET users/:id/subscription-request-history` | История обращения к подпискам |
| `POST bandwidth-stats/nodes/usage` | Статистика трафика пользователей по нодам |

Оригинальная логика Limiter 5.1.0 отвечает за IP/ASN группировку, предупреждения, режимы manual/auto, временные блокировки и автовосстановление, поиск аномального трафика, повторных пробных подписок по общему HWID, Telegram-уведомления и inline-кнопки.

### Настройки через интерфейс

Во вкладке `Инструменты → Limiter` задаются:

- Режим, интервал, окно активности IP, HWID-лимиты, допуски, порог и окно нарушений, cooldown от 1 секунды и время автовосстановления.
- IPv4 подсети, ASN, исключённые IP/CIDR, пользователи и ноды.
- Аномальный трафик, общий HWID, мониторинг повторных пробных периодов.
- Telegram Bot Token, Chat ID, Admin IDs; при необходимости MaxMind License Key и UUID сквадов.

Сначала сохраните Telegram Bot Token, Chat ID и Admin IDs кнопкой **Сохранить Telegram / MaxMind**: Telegram обязателен для оригинального Limiter. Выберите ручной режим, включите переключатель Limiter и нажмите **Сохранить настройки**. После следующей проверки runner нажмите **Обновить** и проверьте состояние процесса и сообщение об ошибке. Получение Telegram-уведомлений подтвердите на тестовом пользователе, после чего включайте нужные дополнительные функции.

Telegram/MaxMind-ключи вводятся в UI, шифруются AES-256-GCM в PostgreSQL и не возвращаются в форму. Для шифрования используется стабильный `REMNADROP_LIMITER_ENCRYPTION_KEY` длиной от 32 символов; если он не задан, используется `APP_SECRET` или `JWT_AUTH_SECRET`. Ключ шифрования хранится в конфигурации панели и должен сохраняться при обновлениях и восстановлении БД.

### Обновление после успешных проверок выбранной ревизии

```bash
cd /opt/remnadrop-git
git switch main
git pull --ff-only origin main
sudo install -m 755 scripts/remnadrop-cli.sh /usr/local/bin/remnadrop
sudo remnadrop check
sudo remnadrop update
```

Установщик проверяет запас диска, создаёт резервные копии, тестирует восстановление PostgreSQL, выполняет миграции и пересоздаёт сервис панели. Успех требует совпадения фактического ID образа и здорового состояния контейнера. После обновления:

```bash
docker inspect remnawave --format 'Image={{.Config.Image}} ID={{.Image}} Health={{.State.Health.Status}}'
docker exec remnawave test -x /usr/local/bin/remnawave-limiter
docker exec remnawave test -s /etc/ssl/certs/ca-certificates.crt
```

Эти команды подтверждают состояние контейнера и состав образа. Наличие бинарника и отображаемая версия `5.1.0` сами по себе не подтверждают работоспособность внешних токенов, Telegram и нод. Реальный запуск, уведомления, отключение и восстановление тестового пользователя проверяются отдельно. Пока переключатель Limiter выключен, проверки подключений пользователей не запускаются.

## Cloudflare DNS

**Инструменты → Cloudflare DNS** показывает зоны, записи A/AAAA/CNAME, поддомены, связи с хостами и нодами, а также историю операций. Если записи отдельной зоны не загрузились, интерфейс показывает ошибку этой зоны.

Введите Cloudflare API Token в UI с разрешениями **Zone Read, DNS Read, DNS Edit** для нужных зон. Токен проверяется через Cloudflare и хранится зашифрованным. Ключ шифрования — стабильный `CLOUDFLARE_DNS_ENCRYPTION_KEY` длиной от 32 символов, с альтернативой `APP_SECRET` / `JWT_AUTH_SECRET`. В исходниках и командах установки токены не задаются.

Zone ID можно изменить с проверкой соответствия домену. Сопоставление использует **host.address**, CNAME и явные привязки записи к хосту; SNI и HTTP Host не участвуют. Явная привязка учитывает одновременно **Zone ID и Record ID**. У хоста должна быть задана связь с нодой через поле «Ноды»; связь только через inbound в этом механизме не используется.

Замена IP разрешена для A/AAAA-записи, связанной с указанной нодой. **Общая запись, связанная с несколькими нодами, отклоняется** — для независимого изменения нужны отдельные записи и привязки. Непосредственно перед PATCH повторно проверяются ожидаемый старый IP, имя и тип записи. Это повторная проверка состояния, **не атомарный compare-and-swap**: параллельное изменение во внешнем редакторе между проверкой и PATCH всё ещё возможно. PATCH меняет только адрес, сохраняя остальные параметры записи.

Автозамена IP работает при двух явных условиях: `auto_sync` на зоне Cloudflare и `updateCloudflare` в действии `rotate_ip`. При совпадении старого IP изменяется только A-запись, привязанная к хосту нужной ноды. Посторонние DNS-записи не затрагиваются. История сохраняется в `cf_dns_events`.

Управление токеном, зонами и привязками доступно администратору. `POST /api/cloudflare-dns/replace-ip` также доступен API-токену с правом **`hosts:cloudflare-replace-ip`**. Тело запроса содержит `zoneId`, `recordId`, `nodeUuid`, `expectedOldIp`, `newIp`.

- Входящий вебхук: `POST /api/cloudflare-dns/webhook/node-ip-changed`, ключ `CLOUDFLARE_DNS_INCOMING_SECRET`. Проверяются HMAC исходного тела, время и идентификатор события; повторная доставка учитывается.
- Исходящий вебхук: событие `CLOUDFLARE_DNS_IP_UPDATED`, адрес `CLOUDFLARE_DNS_WEBHOOK_URL`, ключ `CLOUDFLARE_DNS_WEBHOOK_SECRET`.

## Главная и интерфейс

На Главной отображается использование доступного пространства файловой системы панели. Дополнительные диски можно показать через read-only mounts + `REMNADROP_DISK_PATHS`. Кнопка поддержки подписана «Поддержать проект» на десктопе; Telegram-ссылка — [RemnaDrop](https://t.me/remnadrop).

## Проверки перед production

1. CI Dockerfile.dev / NestJS / frontend / Prisma генерация, наличие бинарника Limiter и CA-сертификатов в итоговом образе.
2. Миграция на восстановленном клоне PostgreSQL Remnawave 2.8.1.
3. Limiter включён/выключен через UI; процесс в контейнере `remnawave`; подключение Valkey по Unix-сокету или TCP и DB 8; ошибка в настройках не останавливает панель.
4. Безопасность HMAC/Bearer, отключение/восстановление тестовых пользователей, Telegram, трафиковые алерты, общий HWID.
5. Cloudflare DNS: Zone ID, домены и поддомены, CNAME, явные привязки, повторная проверка старого IP перед PATCH, отказ для чужих и общих записей, HMAC, таймаут и повтор события. Реальную запись проверяют на специально выбранном тестовом DNS-имени.
6. Работа в браузере с мобильных устройств и после обновления страницы.

Источники: upstream [Limiter 5.1.0](https://github.com/syvlech/remnawave-limiter/releases/tag/5.1.0), документация [Cloudflare DNS API](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/edit/).
